MySQL 索引失效的常见写法

2026.09.15 后端 16 min read

"我明明加了索引，为什么还是慢？"——这是我在排查慢查询时最常遇到的情况。 索引存在 ≠ 索引生效，优化器在评估成本后完全可能选择放弃它。

这篇把我实际踩过的失效场景整理一遍，每个都给出复现 SQL 和判断依据。

一、先用 EXPLAIN 说话

不要靠感觉猜。在 MySQL 8 里用 EXPLAIN ANALYZE 能直接看到实际执行耗时， 比传统 EXPLAIN 的估算值更可靠。 

EXPLAIN ANALYZE
SELECT id, name, created_at
FROM users
WHERE DATE(created_at) = '2026-09-01';

关注三个字段：type（出现 ALL 就是全表扫描）、 key（实际使用的索引，为 NULL 说明没用上）、 rows（预估扫描行数，越接近总行数越危险）。

二、在索引列上做运算或调函数

这是最经典的一种。索引里存的是列的原值， 一旦你把它包进函数，B+ 树就没法按顺序定位了。 

-- 失效：索引列被 DATE() 包裹
SELECT * FROM users WHERE DATE(created_at) = '2026-09-01';

-- 生效：改写成范围查询
SELECT * FROM users
WHERE created_at >= '2026-09-01 00:00:00'
  AND created_at <  '2026-09-02 00:00:00';

同理还有 WHERE id + 1 = 10、WHERE YEAR(created_at) = 2026， 都是把索引列变成了表达式。改写的方向只有一个：让索引列单独出现在比较符号的一侧。

三、隐式类型转换

这个坑很隐蔽，因为 SQL 看起来完全正常。当字符串列和数字比较时， MySQL 会把列转成数字，而不是把参数转成字符串—— 于是又变成了"在索引列上做运算"。 

-- phone 是 VARCHAR(20)，且建了索引
SELECT * FROM users WHERE phone = 13800138000;   -- 失效

-- 显式加引号
SELECT * FROM users WHERE phone = '13800138000'; -- 生效

反过来，如果列是 INT 而参数是字符串 '123'， 转换方向对索引友好，索引仍然可用。所以规律是： 参数类型要跟列类型一致，拿不准就加引号。

四、前导模糊匹配

B+ 树是按前缀有序的，LIKE '%abc' 无法确定从哪个位置开始找。

写法索引说明
LIKE 'abc%'生效前缀确定，可范围扫描
LIKE '%abc'失效前缀未知
LIKE '%abc%'失效同上

真要支持全文模糊搜索，应该上全文索引（FULLTEXT）或者独立的搜索引擎， 而不是在大表上硬扛 LIKE '%x%'。

五、OR 连接了未索引的列

-- name 有索引，remark 没有
SELECT * FROM users WHERE name = 'qianmi' OR remark = 'x';  -- 失效

-- 方案一：给 remark 也加索引
-- 方案二：拆成 UNION
SELECT * FROM users WHERE name = 'qianmi'
UNION
SELECT * FROM users WHERE remark = 'x';

只要 OR 两侧有一侧走不了索引，整个查询就只能全表扫描。 优化器不会帮你拆，得自己动手。

六、联合索引的最左前缀

建了 (a, b, c) 的联合索引，等价于建了 (a)、(a,b)、(a,b,c) 三个索引。 跳过 a 直接查 b，索引就用不上。 

-- 索引：(user_id, status, created_at)

WHERE user_id = 1 AND status = 2              -- 生效（用到前两列）
WHERE user_id = 1 AND created_at > '2026-01'  -- 部分生效（只用 user_id）
WHERE status = 2 AND created_at > '2026-01'   -- 失效（跳过最左列）
注意第二行：user_id 用上了索引，但 created_at 没走索引。 因为中间跳过了 status，B+ 树在 user_id 相同的区间内 并不按 created_at 有序。

七、范围查询之后的列

这条经常和上一条一起出现。在联合索引里，一旦某一列用了范围条件， 它后面的列就无法再用于精确定位，只能回表后过滤。 

-- 索引：(a, b, c)
WHERE a = 1 AND b > 10 AND c = 3

这里 a 和 b 用上了索引，c = 3 只能在回表后筛。 所以联合索引的列序设计要遵循：等值条件在前，范围条件在后。

八、其他容易忽略的点

  • IS NULL / IS NOT NULL：单列索引下通常仍可走索引，但选择性差时优化器会放弃。
  • NOT IN / !=：无法使用索引做范围扫描。
  • 字符集不一致的 JOIN：两表关联列字符集不同会触发隐式转换，导致被驱动表的索引失效。
  • 数据量太小或选择性太差：优化器判断走索引比全表扫更贵，主动放弃。

九、小结

所有失效场景其实可以归到一句话：优化器无法利用 B+ 树的有序性去缩小扫描范围。 要么是索引列被包在表达式里、要么是最左前缀被跳过、 要么是范围条件截断了后续列的有序性。

排查时不要背清单，直接看 EXPLAIN 的 key 和 rows， 再用上面的规律反推原因，会快得多。
