XSS-labs 20 关通关总结

2026.08.27 Web 安全 18 min read

XSS-labs 是一个本地 PHP 环境的反射型 XSS 专项靶场。 它的判定机制很有意思：靶场重写了 window.alert， 只要你的 payload 成功触发一次 alert()，就自动跳到下一关。

做之前先把 SQL-labs 过了一遍，上手很快——因为很多关卡的思路本质是一样的： 闭合原有语句，插入自己的代码。区别只在于闭合的是标签、属性，还是 JS 字符串。

下面我不按关卡编号讲，而是按防御手法分组。 因为真正有价值的不是"第几关怎么过"，而是"这种过滤为什么挡不住"。

第一组：零过滤与属性注入（L1–L4）

L1 是最裸的：$_GET["name"] 直接 echo 到页面上，没有任何处理。 

<script>alert(1)</script>

L2 把输出点挪进了 <input value="..."> 里。 标题部分用了 htmlspecialchars，但拼接 value 属性时忘了过滤。 这时候插入标签是没用的，得先闭合属性： 

1"><script>alert('xss')</script>

L3 两处都加了 htmlspecialchars，但它默认是 ENT_COMPAT 模式—— 只转义双引号，不转义单引号。而输出点恰好包在单引号里，于是： 

1' onclick='alert(1)

L4 又变回双引号包裹，但这次单双引号都被转义了。解法是绕开引号—— 用事件属性 + 无引号形式，或者直接闭合标签另起一个： 

1"><script>alert(1)</script>
这一组要建立的核心直觉是：先看输出落在什么上下文里。 上下文是 HTML 正文、属性值、还是 JS 字符串，决定了你需要闭合什么。

第二组：标签与关键字黑名单（L5–L8）

L5 开始出现过滤了：script 关键字被替换。 应对方式有好几种，最直接的是大小写混淆： 

<ScRiPt>alert(1)</ScRiPt>

如果大小写也被处理了，就换非 script 标签。能被浏览器执行 JS 的标签和属性很多： 

<img src=1 onerror=alert(1)>
<svg onload=alert(1)>
<body onpageshow=alert(1)>
<details open ontoggle=alert(1)>
<video><source onerror=alert(1)>

L7 把 script、on 这类词都做了替换，但替换是一次性的， 没有循环处理。于是双写就能恢复： 

<scscriptript>alert(1)</scscriptript>
<img src=1 oonnerror=alert(1)>

L8 引入了 HTML 实体编码。这时候需要看后端解码发生在哪一步—— 如果先解码再过滤，可以用实体绕过；如果先过滤再解码，就换个思路， 利用 javascript: 伪协议或 data: URI 做跳转。

第三组：编码与实体陷阱（L9–L12）

这一组的关键是理解过滤和浏览器解析不在同一个层面。 后端按字符串匹配做黑名单，浏览器按 HTML/JS 语法解析。 只要两者对"同一个输入"的理解不一致，就存在绕过空间。

L9 检查了输入里是否包含 http://，看起来是在防止外链注入。 但它漏了一个基本事实：URL 里可以不写协议头。 

javascript:alert(1)
// 或用实体避开关键字匹配

L11 出现了隐藏字段 t_link、t_history， 服务端只检查 t_ref 参数。用浏览器开发者工具 直接改掉隐藏字段的 value，再提交即可。 这关教的是：永远不要信任客户端提交的任何字段，包括隐藏字段。

第四组：协议与 DOM 型（L13–L16）

L13 起进入 DOM 型 XSS 的地盘。这类漏洞的特点是 服务端完全没有参与——数据从 location.hash 或 innerHTML 直接流向危险汇聚点（sink）。

常见的危险 sink 有：

  • innerHTML / outerHTML / document.write
  • eval / setTimeout(字符串)
  • location.href / location.assign（伪协议）
  • element.setAttribute('onclick', ...)

L16 的 img 标签被过滤了，但过滤规则只针对小写的 img。 换成 <IMG>，或者干脆换 <svg> 就能过： 

<svg onload=alert(1)>
<IMG SRC=x ONERROR=alert(1)>

第五组：进阶与综合（L17–L20）

最后几关把前面积累的手法组合起来，重点考察两点： 一是搞清楚数据流经的每一步做了什么处理， 二是善用浏览器开发者工具观察 DOM 变化。

实战中我会按这个顺序排查：

  1. 输入一个带特征的字符串（比如 qianmi123），看它在页面哪里回显。
  2. 确定回显位置所在的上下文（正文 / 属性 / JS / URL）。
  3. 逐字符试探哪些符号被过滤了：< > " ' ( ) / =。
  4. 根据可用符号构造最小 payload，再逐步升级。

防御：从靶场回到工程

靶场是为了让你看清"为什么挡不住"。真做工程时，防御的优先级应该是：

措施作用注意
输出编码最核心，按上下文选择编码方式HTML/属性/JS/URL 四种上下文编码规则不同
富文本白名单过滤允许部分 HTML 时使用必须用成熟库，别自己写正则
CSP兜底，阻断内联脚本执行配置要严，避免 unsafe-inline
HttpOnly Cookie降低 XSS 窃取会话的危害只是缓解，不是修复
一个常见误区：把黑名单当成主要防御手段。 黑名单永远在追赶攻击者的新花样，而白名单 + 上下文编码 是从语法层面堵死，这才是根本解。

小结

20 关做下来，最大的收获不是攒了一堆 payload， 而是形成了一套上下文优先的思考方式： 先判断数据落在哪，再决定怎么闭合，最后才考虑怎么绕过过滤。

顺序反了，就会变成到处试 payload 的碰运气。
