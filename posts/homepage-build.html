从零搭一个黑底终端风格的个人博客

2026.10.02 杂谈 14 min read

这个博客的视觉，是我先想清楚要什么、再让 AI 把代码写出来的。 配色、形状、版式的取舍由我拍板，HTML / CSS / JS 的实现交给 AI。 这个分工对我刚好合适：我负责"要什么"，AI 负责"怎么写"。

所以这篇不聊成品长什么样，聊从零开始的过程—— 如果让我再空手搭一遍，我会按什么顺序走、每一步分别在决定什么。

一、先定设计意图，再动代码

我想要的是一种纯黑终端、荧光绿做唯一强调色、用锐利斜线切割画面的技术海报感。 这个方向是我自己挑的：我要它一眼看上去像"工程现场"，而不是"设计师作品集"。 方向定下来之后，我给自己立了三条约束：

  1. 只有三种颜色：纯黑、纯白、荧光绿。灰阶只允许作为过渡，不允许出现第四种色相。
  2. 绿色只做强调：面积占比压在 10% 上下。它一旦变成主色，页面就从"克制的技术感"滑向"廉价的赛博朋克"。
  3. 拒绝圆角与规整：容器、色块、过渡带一律带角度，横平竖直只留给文字排版。

第三条是这套视觉的核心。人眼对斜线比直线敏感得多， 一条 30 度的切割线能让整块版面立刻"活"过来——这也是它看起来"有速度感"的根本原因。 先想清楚"什么不允许出现"，比想"要加什么"更重要。

二、把设计意图翻译成 token

意图定完，第一件事不是写组件，而是把它翻译成一组 CSS 变量。 颜色、字体、间距全部收进变量，之后所有组件只引用变量—— 换配色只改一处，也让前面那三条约束变成代码里看得见的东西。 

:root {
  --bg:    #050706;   /* 基底：近黑 */
  --bg-2:  #0b0e0c;   /* 交替区块：比基底亮一档 */
  --paper: #ffffff;   /* 纯白：主文字与碎片 */
  --neon:  #00ff41;   /* 荧光绿：唯一强调色 */

  --mono: "JetBrains Mono", ui-monospace, Consolas, monospace;
  --cjk:  "Noto Sans SC", -apple-system, "PingFang SC", sans-serif;

  --cut:  18px;       /* 斜切角尺寸 */
  --ease: cubic-bezier(0.16, 1, 0.3, 1);
}

这里有个我自己很满意的细节：区块之间不是用边框分隔的，而是靠 --bg → --bg-2 → --bg-3 → --bg-4 四档近黑的明度差。 纯黑底上画白色边框会显得脏，而极小的明度差既能划出层次，又不会破坏"整体是一块黑"的观感。

三、几何碎片场：用代码画，不用贴图

首页背景那片放射状的黑白碎片，是整套视觉里最"唬人"的部分， 也是我从一开始就决定不找素材图的地方。原因有三个： 图片体积大、无法随窗口自适应、而且角度是固定的，换到不同尺寸的容器里立刻露馅。

我的做法是让代码去画。和 AI 来回迭代了几版之后， 最终稳定成三种基本形状：闪电、细长三角、楔形。它们都从一个焦点出发，沿主方向飞散。 

/* 闪电：中轴按折线摆动，宽度从根部渐缩到尖端收 0 */
function bolt(rnd, bx, by, ang, len, w0, kink) {
  var dx = Math.cos(ang), dy = Math.sin(ang);
  var nx = -dy, ny = dx;

  var stops = [0, 0.26, 0.5, 0.74, 1];
  var zig   = [0, kink, -kink * 0.8, kink * 0.55, 0];
  var spine = [];

  for (var i = 0; i < stops.length; i++) {
    var t = stops[i] + (rnd() - 0.5) * 0.05;
    spine.push([
      bx + dx * len * t + nx * zig[i],
      by + dy * len * t + ny * zig[i]
    ]);
  }
  /* 右侧边（根→尖）→ 尖端收成一点 → 左侧边（尖→根） */
  // ... 拼成闭合多边形返回
}

三个参数决定了最终观感：

  • kink 控制闪电的折角幅度。太小看着像普通直线，太大就断了，18 ~ 26 是甜区。
  • len 要拉到足够跑出画布，这样碎片看起来才是"从画面外冲进来"的，而不是悬浮的贴纸。
  • w0 是根部宽度，配合 (1 - t) 的线性收缩，让每根闪电都是"根粗尖细"，自带方向感。

但真正让画面变好看的不是形状，而是分布。最早我是从一个焦点往外撒， 结果所有元素抱团挤在中心，四周一片空。后来写了个分层网格散布函数： 

/* 把画布切成 cols×rows 格，每格取抖动后的中心点，再洗牌打乱顺序 */
function scatter(rnd, cols, rows, jitter) {
  var out = [];
  for (var i = 0; i < cols; i++) {
    for (var j = 0; j < rows; j++) {
      out.push({
        x: (i + 0.5 + (rnd() - 0.5) * jitter) / cols,
        y: (j + 0.5 + (rnd() - 0.5) * jitter) / rows
      });
    }
  }
  // Fisher-Yates 洗牌，避免"按格子顺序铺"的规律感
  return out;
}

这一改动的效果是决定性的：元素从"中心一团"变成"铺满全屏但疏密有致"。 jitter 的作用是打破网格的规整感，让分布看起来是随机的而不是排出来的。

随机数用的是 mulberry32 这类带种子的伪随机， 而不是 Math.random()。这样每个页面配一个固定的 seed， 每次刷新长得一模一样；否则用户每刷新一次背景就换一个样，会显得很廉价。 同时它也保证了"同一个 seed 必然复现同一张构图"，方便调参。

四、锐角化：clip-path 与斜切过渡带

全站拒绝圆角，靠的是 clip-path。按钮、卡片、图片容器都切掉对角： 

.btn {
  clip-path: polygon(
    0 0, calc(100% - var(--cut)) 0, 100% var(--cut),
    100% 100%, var(--cut) 100%, 0 calc(100% - var(--cut))
  );
}
.btn:hover {
  transform: translate(-4px, -4px);
  box-shadow: inset 0 0 0 2px var(--neon), 5px 5px 0 var(--neon);
}

悬停时向左上位移、右下角投出一块实心荧光绿阴影—— 这种"错位硬阴影"是海报排版的常用手法，比柔和的 box-shadow 更符合锐利的调性。

区块之间的斜线接缝，用了一个很省事的技巧：一个容器，背景是上一块的颜色， 内部伪元素铺满并填下一块的颜色，再给它一个三角形裁切。 

.slant {
  position: relative;
  height: clamp(38px, 5vw, 78px);
  background: var(--a);          /* 上一块的颜色 */
}
.slant::after {
  content: "";
  position: absolute;
  inset: 0;
  background: var(--b);          /* 下一块的颜色 */
  clip-path: polygon(0 100%, 100% 0, 100% 100%);
}

这样接缝天然严丝合缝，不用算负 margin，也不怕响应式下高度变化。

五、我定规则，AI 写实现

整套东西的代码是 AI 写的，但它写什么、按什么规则写，是我定的。 这个分工值得说清楚，因为它决定了成品像不像"我的东西"。

我做的事：定三条颜色约束、定形状只用闪电 / 三角 / 楔形、定绿色占比上限、 定"碎片必须铺满全屏且疏密有致"、定每个页面的 seed 不能重复。 这些是设计意图，也是我 review 代码时的验收标准。

我交给 AI 做的事：把约束翻译成几何计算、写出生成器函数、 实现 clip-path 的锐角裁切、把响应式断点补齐。 这些是实现细节——我只要结果符合约束，不关心它用哪种写法。

这套流程能成立的前提是：你得能判断结果对不对。 我能看出"碎片抱团了""绿色太多了""这个角不够锐"， 所以才能给出有效的修改意见。如果连好坏都分不出来， AI 生成的再多，也只能照单全收。

六、零依赖、零构建

整个站点最后是：一个 CSS 文件、一个 JS 文件、几个 HTML 页面。 没有 npm，没有打包器，没有框架，没有构建步骤。

这个选择不是"反工程"，而是匹配需求。博客是纯静态内容站， 没有状态管理、没有路由、没有数据请求——引入一套前端工具链， 换来的是每次改一篇文章都要等构建，以及一个几百 MB 的 node_modules。 对一个只有几个页面的站点来说，这笔账不划算。

代价是要手写一些重复的 HTML（比如每个页面都要复制导航和页脚）。 但对这个体量来说，重复的成本远低于维护一套模板引擎或静态站点生成器。 知道什么时候不该上工具，和会用工具同样重要。

七、部署：让它一直在线

站点托管在 GitHub Pages 上，仓库名必须是 <用户名>.github.io 这个固定格式，这样访问地址就是干净的 https://用户名.github.io，不带任何子路径。

有两个文件是部署前必须准备好的：

  • .nojekyll：一个空文件，告诉 GitHub Pages 跳过 Jekyll 处理，直接按静态文件原样发布。没有它，以下划线开头的文件或目录会被吞掉。
  • .gitignore：挡掉系统文件和编辑器配置，避免把无关内容提交上去。
# 首次发布
git init -b main
git add -A
git commit -m "init: blog"
git remote add origin https://github.com/<用户名>/<用户名>.github.io.git
git push -u origin main

# 之后每次更新文章，只要三条命令
git add -A
git commit -m "post: 新增文章 xxx"
git push

推送完成后，GitHub 会自动触发一次构建，一两分钟后新内容就生效， 不需要在仓库设置里反复操作。Pages 是免费的，也没有到期日—— 只要仓库还在，站点就一直在线。

实际部署时会遇到一个和代码无关的坑：国内网络访问 GitHub 不稳定， 表现为 TCP 能握手但 TLS 请求被间歇性掐断，git push 时不时失败。 这不是配置错误，重试通常就能过。另外要记住：这种不稳定只影响上传， 站点发布后是由 GitHub 的 CDN 对外服务的，和本地网络无关，访问速度不受影响。

结语

回过头看，这个项目里真正花时间的不是写代码，而是做决定： 用几种颜色、绿色占多少、碎片怎么分布、区块怎么衔接。 代码只是这些决定的结果——这也是为什么 AI 能替我把代码写完， 却替不了我做这些判断。

如果你也想做类似的视觉，建议从先定约束开始—— 规定好"只能用哪三种颜色""哪些形状禁止出现""什么情况下不加元素"， 剩下的决定会突然变得容易很多。
